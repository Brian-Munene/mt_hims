## Backend (avocent-backend/)

### Development

```bash
python3.12 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
cp .env.local.example .env.local
python manage.py generate_keys --path .env.local   # writes SECRET_KEY, API_ENCRYPTION_KEY, FIELD_ENCRYPTION_KEY
# edit .env.local for local Postgres/Redis, then:
set -a && source .env.local && set +a
python manage.py migrate
python manage.py runserver  # http://localhost:8000; Swagger at /api/docs/swagger/
```

### Tests

```bash
pip install -r requirements-dev.txt
python manage.py test                          # full suite (151 tests)
python manage.py test users.tests              # one app
python manage.py test users.tests.test_serializers  # one module
coverage run manage.py test && coverage report
```

CI requires `SECRET_KEY`, `API_ENCRYPTION_KEY`, and `FIELD_ENCRYPTION_KEY` — they're generated by `generate_keys` and exported into `GITHUB_ENV`.

### Stack

Django 5.2 · PostgreSQL only (no SQLite fallback) · Redis (cache + Celery broker) · `drf-spectacular` (Swagger/ReDoc) · `djangorestframework-simplejwt` + DRF token + session auth.

### Architecture

**`CoreModel`** (`core/models.py`) is the abstract base for almost every domain model: UUID pk, `clinic` FK (organization.Clinic), `created_at`, `updated_at`, `created_by`, `is_active`, `metadata`.

**`ClinicScopedModelViewSet`** (`core/api.py`) is the standard ViewSet base. It:
- Filters `get_queryset()` to `clinic_id=request.user.clinic_id` for all non-superusers.
- Forces `clinic=request.user.clinic` on `perform_create` and `perform_update`, overriding any client-submitted value. This is intentional; never skip it.
- Sets `created_by` automatically.
- Uses `ClinicRBACPermission` backed by `users.access.can_access_object` / `users.permissions.has_permission`.

**Clinic scoping in serializers** (`core/serializers.py`): `resolve_effective_clinic` mirrors the ViewSet's forced-clinic logic for use inside `validate_*` methods. Use `validate_clinic_match` to reject cross-clinic FK relationships before save. Always pair these with the ViewSet's own enforcement — serializer validation alone is not enough.

**Celery** (`avocent_backend/celery.py`): appointment reminders, M-PESA callback processing, lab result notifications, hourly compliance auto-flagging (Beat). Requires `REDIS_URL`; without it scheduling is skipped silently. `CELERY_TASK_ALWAYS_EAGER=true` in tests.

**AES-256-GCM API payload encryption** (`core/middleware.py`, `core/encryption.py`): optional transport layer on top of TLS, disabled by default. `API_ENCRYPTION_ENABLED=true` + `API_ENCRYPTION_KEY` to enable; `API_ENCRYPTION_ENFORCE=true` to reject plaintext writes. Docs/schema endpoints are always excluded.

**Field-level PHI encryption** (`core/fields.py`): encrypts sensitive fields at rest using `FIELD_ENCRYPTION_KEY`.

### E2E tests (Playwright — requires full stack running)

Playwright does **not** start the stack — bring it up first, then seed the test user:

```bash
# 1. Start the stack — pick one:
#    Native:  manage.py runserver  +  npm run dev
#    Compose: docker compose --env-file .env.local -f docker/compose.yml -f docker/compose.local.yml up
#    k8s:     kubectl port-forward -n avocent svc/<release>-web 8000:8000 &
#             kubectl port-forward -n avocent svc/<release>-frontend 3000:3000

# 2. Seed the test user (idempotent — safe to re-run, run from avocent-backend):
python manage.py seed_e2e_user

# 3. Run (from avocent-frontend):
npm run test:e2e                        # headless, serial (default — safe for native dev server)
CI=true npm run test:e2e                # parallel workers (Compose/k8s/gunicorn only)
E2E_BASE_URL=http://staging:3000 npm run test:e2e   # target a non-localhost stack
npm run test:e2e:ui                     # interactive Playwright UI
npm run test:e2e:report                 # view last HTML report
```

**Test user:** `e2e@avocent.test` / `E2E-test-pass-123!` — defined in `e2e/fixtures.ts`, created by `seed_e2e_user`. Never run that command against a real clinic database.

**Spec files:**
- `auth.spec.ts` — login success/failure, protected-route navigation, logout, and two token-refresh regression cases: an expired access cookie with a live refresh cookie must silently re-issue (not redirect to login); a dead refresh cookie must log out cleanly without looping.
- `clinical-flow.spec.ts` — receptionist desk flow: register a patient, book them in as a walk-in, confirm both records surface in their respective list/search views. Cleans up its own records in `afterEach` so repeat runs don't accumulate data.

**Cookie name overrides:** `JWT_ACCESS_COOKIE` and `JWT_REFRESH_COOKIE` env vars let you point the fixtures at a stack configured with non-default cookie names.

### Architecture

**Auth flow**: Browser → `POST /api/auth/login` (Next.js Route Handler) → exchanges for Django JWTs → stored as httpOnly cookies. Server Components read cookies directly; browser-side mutations go through `src/app/api/*` route handlers, which proxy to Django.

**Route groups**:
- `src/app/(auth)/` — login, logout, forgot-password, reset-password
- `src/app/(dashboard)/` — all authenticated clinic modules; one subdirectory per domain (patients, booking, encounters, clinical, billing, pharmacy, laboratory, telemedicine, compliance, queue, admin)
- `src/app/api/` — Route Handlers (BFF proxy to Django)

**Key libs**:
- `src/lib/api/` — typed fetch wrappers for each Django resource
- `src/lib/rbac.ts` — role checks aligned to backend roles
- `src/lib/auth.ts` — `requireUser()` / `maybeUser()`, session cookie helpers
- `src/lib/encryption.ts` — client-side AES-256-GCM for the optional encrypted API transport

**Stack**: Next.js 16 App Router · React 19 · TypeScript · Tailwind CSS v4 · shadcn/ui · React Hook Form + Zod · Zustand.

## Docker Compose

Run from `avocent-backend/`:

```bash
# Local
docker compose --env-file .env.local -f docker/compose.yml -f docker/compose.local.yml up --build

# Staging / prod — replace compose.local.yml with compose.staging.yml / compose.prod.yml
```

`entrypoint-web.sh` runs `migrate` + `collectstatic` before gunicorn. Staging/prod add Caddy for automatic TLS. `ALLOWED_HOSTS` must include `web` (the internal service name the frontend container uses).

## Kubernetes (Helm)

One Helm release = one clinic stack.

```bash
# Build and load images into a local kind cluster, then install:
docker build -f avocent-backend/docker/Dockerfile -t avocent-backend:helm avocent-backend
docker build -t avocent-frontend:helm avocent-frontend
docker save avocent-backend:helm | docker exec -i desktop-control-plane ctr --namespace k8s.io images import -
docker save avocent-frontend:helm | docker exec -i desktop-control-plane ctr --namespace k8s.io images import -
helm install avocent-local deploy/helm/avocent -n avocent --create-namespace -f deploy/helm/values-local.yaml
```

`beat` is pinned to 1 replica (Recreate) to prevent double-firing. For production, use an external Postgres (`postgres.internal: false`) and enable `ingress` with cert-manager.

## Terraform (infra/terraform/)

Provisions the Azure infrastructure that the Kubernetes cluster runs on. Separate from `deploy/helm/` — Terraform owns the platform layer (AKS cluster, networking, Azure AD identities, managed databases), Helm owns the application layer on top of it.

Structure:
- `bootstrap/` — run once first; creates the Azure Storage backend for Terraform state and the service principal used by subsequent applies
- `environments/staging/` and `environments/production/` — environment configs; each calls shared modules

Providers: `azurerm` (AKS, storage, networking), `azuread` (identities/RBAC), `helm` + `kubernetes` (deploys the Helm chart from within Terraform).

```bash
cd infra/terraform/environments/staging   # or production
terraform init
terraform validate
terraform plan
```

## Custom agents

`.claude/agents/` contains two project-aware subagents invoked automatically by Claude Code:

- **`code-reviewer`** — read-only diff reviewer; checks correctness, security, clinic scoping enforcement, and N+1 queries. Invoke with `/code-review` before any commit.
- **`test-runner`** — runs `python manage.py test`, diagnoses failures, and re-runs until green. Uses Django's test runner (not pytest). Invoke after any logic change to backend app code.
