1. ~~**Design and wire up a ComplianceRecord auto-flagging mechanism.**~~ — **RESOLVED.** Per your call: a scheduled rule flags outpatient encounters whose bill and encounter both remain unclosed for over 24 hours. Implemented as `compliance/tasks.py::flag_overdue_outpatient_encounters`, a Celery Beat task running hourly (`avocent_backend/celery.py::app.conf.beat_schedule`, `crontab(minute=0)`). Rule: any `Encounter` with `status="active"` and `start_time` more than 24h ago, where none of its related `Invoice`s have reached a closed state (`status` in `paid`/`void`) — covers both "no invoice raised at all" and "invoice still draft/unpaid." Creates a `ComplianceRecord(resource_type="encounters.encounter", resource_id=<encounter id>)`; skips encounters that already have an **open** flag so re-runs don't create duplicates.
   - **Verified end-to-end** against a real local Celery worker connected to Redis (not mocked): 4 test scenarios (overdue+no-invoice, overdue+draft-invoice, overdue+paid-invoice, not-yet-overdue) all flagged/skipped correctly, a second run created 0 duplicate flags, and all test data was cleaned up afterward.
   - **Scope note:** no inpatient/admission concept exists anywhere in this codebase (only `encounter_type`: in_person/video/audio, a delivery-channel field) — every patient in this system is effectively an outpatient, so the rule applies to all active encounters with no extra filtering needed.

2. ~~**Deploy Celery + a real broker**~~ — **RESOLVED.** Per your call: Redis + Celery. This was actually already substantially scaffolded (`avocent_backend/celery.py`, `docker/entrypoint-worker.sh`, `docker/entrypoint-beat.sh`, `docker/compose.*.yml`, and `.env.local`/`.env.staging.example`/`.env.prod.example` already had `REDIS_URL`/`CELERY_BROKER_URL` set) — it just wasn't actually wired correctly or running. Found and fixed the real bug: `encounters/services.py::schedule_appointment_reminder` was gating on `core.tasking.CELERY_AVAILABLE`, which only checks whether the `celery` package is *importable* (it is — both `celery` and `redis` are in `requirements.txt`), not whether a real broker is configured. Without `REDIS_URL`, `CELERY_BROKER_URL` silently falls back to the in-process `memory://` transport, which drops anything scheduled with an `eta` since no separate worker can consume it — so reminders were never actually being skipped *or* delivered correctly, depending on environment.
   - **Fix:** added `settings.CELERY_BROKER_CONFIGURED = bool(REDIS_URL)` and switched `schedule_appointment_reminder`'s gate to check that instead. Updated `encounters/tests/test_services.py` to match (`@override_settings(CELERY_BROKER_CONFIGURED=...)` instead of patching the old flag).
   - **Verified end-to-end**: started a real `celery -A avocent_backend worker` process against the local Redis instance (already running via `redis-server`, confirmed with `redis-cli ping`), dispatched the new compliance task through it with `.delay()`/`.get()`, and confirmed the round-trip works — proving the shared broker/app config works for any task, including `send_appointment_reminder`.
   - **Still needed from you:** the worker + beat processes need to actually be *running* for reminders/compliance-flagging to fire in normal use — either `docker compose -f docker/compose.local.yml up worker beat` (uses `.env.local` automatically) or, for bare `manage.py runserver` dev, export `REDIS_URL`/`CELERY_BROKER_URL`/`CELERY_RESULT_BACKEND` from `.env.local` in the same shell and run `celery -A avocent_backend worker -l info` and `celery -A avocent_backend beat -l info` alongside it (see `README.md` "Run a Celery worker" / "Run Celery Beat" sections, already documented). I did not leave a worker process running after verification.

4. ~~**Handle permission-denied (403 ApiError) gracefully**~~ — **RESOLVED.** `(dashboard)/error.tsx` now has a branch that detects Django's permission-denied wording in `error.message` and renders a friendly "Access denied" card with a link back to `/`, instead of the generic "Dashboard failed to load" message.
   - **Caveat:** Next.js only forwards `message`/`digest` (not custom `ApiError.status`) across the Server→Client error-boundary serialization boundary, and in production builds `error.message` itself is replaced with a generic identifier for Server Component errors (dev mode passes the real message through verbatim, which is what was observed). So this fix works today in local dev, but won't trigger in a production build — making 403s render gracefully in production would require not throwing for expected 403s at all (e.g. catching them per-page and rendering inline, or adopting Next's experimental `forbidden()`/`forbidden.tsx` convention), which is a bigger change than this pass.
